# 02. モジュール境界と env 層の結線

対象: Terraform の module 設計に慣れている前提で、境界線をどこに引くかを判断する材料。

## 1. 2 モジュール構成

```
modules/batch_gpu_compute   … CE + ジョブキュー + SG + 起動テンプレート + インスタンスロール
modules/batch_job           … ジョブ定義 + ジョブロール + 実行ロール + ロググループ
envs/{env}/*.tf             … 上記を呼び、S3 / ECR / VPC と結線
```

境界は **「変更頻度」と「所有者」** で引く。

- `batch_gpu_compute` = インフラ都合で変わる。触ると **実行中ジョブに影響が及ぶ**（CE の置換 → 04）。
- `batch_job` = アプリ都合で変わる。ジョブ定義は新リビジョンが増えるだけで、既存実行に影響しない。

Batch の API 構造（`SubmitJob` がキューとジョブ定義を独立に受ける）と一致するので、境界として自然。ライフサイクルの異なるものを 1 モジュールに閉じ込めない。

## 2. CE を系統ごとに分けるか、ステージ間で共有するか

2 ステージ（前処理 / 埋め込み）を動かす場合、選択肢は 2 つ。

**(a) CE + キューをステージごとに用意**（モジュールを 2 回インスタンス化）
**(b) CE + キューを 1 つ共有し、ジョブ定義だけステージごとに分ける**

| | (a) 分離 | (b) 共有 |
| --- | --- | --- |
| インスタンスタイプの最適化 | ステージごとに選べる | **片方に妥協が出る** |
| EC2 の使い回し | しにくい | 連続実行時にスケールイン前なら使い回せる |
| リソース数 | 倍 | 半分 |
| キュー優先度による制御 | 効く（キュー間の概念） | **効かない**（キューが 1 本） |
| 後から分けるコスト | — | CE 分割 = キュー名変更 = **投入元の設定変更**を伴う |

推論の量子化やモデル差でインスタンスファミリーを変えたくなる見込みがあるなら (a)。当面同じ資源で足りるなら (b) で始めて、必要になった時点で割る判断もある。ただし後から割るとキュー名が変わり、投入元（スケジューラ / Step Functions）に波及することは織り込んでおく。

**ドキュメントと実装が食い違いやすい箇所でもある**。設計メモが (a) を前提に書かれたまま実装が (b) になっている、という不整合は実際に起きた。

## 3. ステージ固有 IAM をどこで組むか

**方式 A（モジュール内で組む）**: env 層は ARN を渡すだけ。ポリシー文書はモジュール内。

```hcl
storage_access = { output_bucket_arn = aws_s3_bucket.this["output"].arn }
execution_role = { ecr_repository_arn         = aws_ecr_repository.this["stage"].arn }
```

**方式 B（ルートで書いて attach）**: env ルートで `aws_iam_policy_document` を書き、モジュールが出力したロール名に `aws_iam_role_policy_attachment` で後付けする。

| 観点 | A: モジュール内で組む | B: ルートで書いて attach |
| --- | --- | --- |
| env ルートの記述量 | 少ない（結線 1 ファイル 100 行未満に収まる） | ポリシー文書がステージ数だけ並ぶ |
| 最小権限の担保 | モジュールが強制するので**外し忘れが起きない**（マルチパートの 3 アクションなど、知らないと漏れる権限を locals に畳める） | 書く人の知識に依存 |
| 想定外の要求への対応 | `additional_policy_arns` の逃げ道はあるが、主要権限は入力の形を変えないと足せない | 何でも足せる |
| モジュールの汎用性 | **低い**。バケット ARN が必須引数なので、S3 を使わないジョブには使えない | 高い |

判断軸は **「このモジュールは組織横断の汎用モジュールか、このプロジェクト専用の内製部品か」** の一点。専用部品と割り切るなら A が正しい。変数が特定の環境変数名やバケット用途を名指ししている時点で、すでに専用部品として設計されている。

レビューで確認すべきは方式そのものの善し悪しではなく、**その前提（専用部品でよい）が合意されているか**。組織内の他プロジェクトが B の流儀で統一されているなら、結線作法が変わることの周知は要る。

## 4. 入力インターフェースの作り方（有効だったパターン）

- **オブジェクト型 + `optional()` でグルーピング**（`compute_environment`, `launch_template`, `storage_access`, `execution_role` …）。フラットな変数を 40 個並べるより読みやすく、既定値を型定義に書ける。ヒアドキュメントの `description` に各キーの意味と既定値を書いておくと `terraform-docs` なしでも読める。
- **`validation` を実質的に使う**。enum チェック、リストの非空、`gpu_count >= 1`、**シークレット ARN の形式チェック**（`can(regex(":ssm:", value))`）。最後のものは「渡し間違えると実行時まで気づけない」種類のミスを plan 時点に前倒しできて効果が大きい。
- **命名は `{microservice}-{env}-{object}-{type}` を locals で組み立てる**。組織の命名規則があるならそれに合わせる。

## 5. env 層で検算すべき数字

結線ファイルには机上検証できる具体値が入る。例（GPU 1 枚 / 4 vCPU / 32 GiB のインスタンスを想定）:

```hcl
instance_types = ["<gpu-instance>.xlarge"]   # GPU 1, vCPU 4, メモリ 32 GiB
max_vcpus      = 8                            # → 同時に 2 台まで
root_volume_size_gibibytes = 300

stage-a: vcpus=4, memory=30720 MiB, gpu=1, timeout=10800s (3h)
stage-b: vcpus=4, memory=15360 MiB, gpu=1, timeout=7200s  (2h)
```

- `vcpus` がインスタンスの vCPU **ちょうど**だと余裕ゼロ。ECS on EC2 は vCPU をオーバーサブスクライブできない。
- `memory` は物理 32 GiB (32768 MiB) から OS / ECS エージェント分を引いた「**ECS が認識する利用可能メモリ**」が上限。AMI とカーネルに依存し、実測では 31000 MiB 前後になることが多い。**1 MiB でも超えるとジョブは `RUNNABLE` から進まず、エラーもほぼ出ない**（→ 05 §4）。
- `max_vcpus` と 1 ジョブの vCPU から同時実行数が決まる。想定運用（直列か並列か）と合っているか。
