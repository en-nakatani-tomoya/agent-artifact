# 06. レビュー観点チェックリスト（AWS Batch GPU × Terraform）

01〜05 を「実際にコメントするなら何を書くか」の形に落としたもの。他プロジェクトの同種 PR にもそのまま流用できる。

---

## A. 必ず聞く（回答次第で判断が変わる）

### A-1. 設計ドキュメントと実装の一致
CE / キューを系統ごとに分けるのか共有するのか、設計メモと結線コードが一致しているか。**設計が先行して書かれ、実装で方針が変わったまま文書が残る**パターンが実際に起きた。共有にした場合、後から分割すると **キュー名が変わり投入元の設定変更を伴う**ことを合意できているか。（→ 02 §2）

### A-2. SPOT とリトライ戦略の整合
`capacity_type = "SPOT"` かつ `evaluate_on_exit` なしだと、Spot 中断もアプリの決定的失敗も等しくリトライされる。長時間ジョブでは GPU の占有コストに直結する。
- `evaluate_on_exit` で「中断のみリトライ」に絞る想定はあるか
- ジョブは途中中断されても再実行で正しく回るか（冪等性・チェックポイント）
（→ 04 §4, 05 §3）

### A-3. メモリ設定の実測確認と初回 apply 手順
ジョブのメモリ要求がインスタンスの「ECS 利用可能メモリ」を超えていると、**`RUNNABLE` から進まずエラーもほぼ出ない**。apply 後にダミージョブを 1 本流して確認する手順があるか。（→ 05 §4）

### A-4. AMI の `recommended` 追従と CE 置換
SSM の `recommended` を参照していると、AWS の AMI 更新日に plan 差分が出て CE が置換される。**バッチ実行中に CI の apply が走った場合、実行中ジョブはどうなる想定か**。`update_policy` を設定するか。（→ 04 §2, §3）

## C. 確認して「問題なし」と言える箇所（追認する）

- **CE の `name_prefix` + `create_before_destroy` + IAM への `depends_on`** — Batch を Terraform で扱うときの定番の罠 3 つへの正しい対処（04 §1）
- **実行ロールとジョブロールの分離**、`AmazonECSTaskExecutionRolePolicy` を使わず ECR / Logs をリソース単位に絞ったこと。`Resource = "*"` は仕様上避けられない `ecr:GetAuthorizationToken` のみ（03 §4）
- **S3 のマルチパートアップロード 3 アクション**を揃えたこと、`s3:ListBucketMultipartUploads` を別ステートメントにしたこと（03 §5c, 5d）
- **Batch サービスロールを SLR に委譲**（現行の AWS 推奨）（03 §3）
- **IMDSv2 必須 + `hop_limit = 2` + EBS 暗号化**。特に hop_limit 2 はコンテナから認証情報を取るのに必須（04 §5）
- **ロググループを Terraform で明示作成し retention を設定**（自動作成任せは無期限保持）（05 §6）
- **`environment` / `secrets` をキーでソート**して差分の揺れを防止（05 §1）
- **シークレット ARN 形式の `validation`**。実行時まで気づけない権限不足を plan に前倒し（02 §4, 05 §7）
- **`bid_percentage` をオンデマンド時に `null` へ潰す**分岐（API エラー回避）（04 §4）

## D. 判断を保留してよい（好みの問題 / 別途合意すべき）

- **ステージ固有 IAM をモジュール内で組むか、ルートで書いて attach するか**。決め手は「汎用モジュールか専用部品か」。専用部品として一貫しているなら方針を明文化すれば足りる（02 §3）
- **タグの例外措置**。事実関係は正しく、モジュールは `var.tags` を透過するだけなので「モジュール内に共通タグを書かない」ルールの精神には反していない（04 §6）
- **SPOT 時に常に Spot Fleet ロールを作る**（現行の配置戦略では不要）。切替時の事故防止 vs 未使用リソース（04 §4）
- **命名スタイルの統一**。組織の命名規則ドキュメントに照らして Type 部分の粒度が揃っているかを見る程度で十分

## E. 手を動かす確認

1. **CI の plan 結果を読む**。ローカルで tflint / trivy を回していない PR では、CI が唯一の検証手段
2. plan の出力で **CE と起動テンプレートが「作成」だけか**を確認（既存リソースの置換が混ざっていないか）
3. **IAM ポリシーの JSON を目視**。`terraform plan` は `aws_iam_policy` の `policy` を展開するので 03 §5 の観点で読める
4. 生成される**リソース名を一覧化**して命名規則と突き合わせる
5. apply 後、**ダミージョブを 1 本投げて `RUNNABLE` を抜けるか**確認（A-3）

---

## F. 「plan が通る」が保証しないこと

Terraform の plan は Batch API の受理可否を検証しない。以下は apply / 実行まで分からない。

- ジョブのメモリ / vCPU 要求がインスタンスの利用可能量に収まるか
- 指定したインスタンスタイプが GPU 要求を満たすか
- CE の置換シナリオが実際に通るか
- SLR が未作成のアカウントで初回 apply が成功するか
- Spot キャパシティが実際に確保できるか

**apply していない PR をレビューするときは、この 5 点を「未検証」として明示的に共有しておく**と、後の障害が「レビュー漏れ」ではなく「既知の未検証項目」になる。
