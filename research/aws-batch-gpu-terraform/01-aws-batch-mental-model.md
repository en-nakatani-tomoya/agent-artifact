# 01. AWS Batch のメンタルモデル（EC2 / GPU 実行）

対象読者: Batch の概念は知っているが実務で触ったことがない人。各リソースが「実行時に誰の役割を果たすか」を掴むのが目的。

## 1. Batch は「スケジューラ + オートスケーラ」であって実行基盤ではない

Batch 自身はコンテナを動かさない。動かすのは **ECS** で、その ECS が載る計算資源は **EC2 Auto Scaling**（実体は EC2 Fleet / Spot Fleet）である。Batch がやるのは次の 2 つだけ。

1. キューに溜まったジョブを見て、**必要な台数の EC2 を勝手に増やし、空いたら勝手に減らす**
2. ジョブの要求リソース（vCPU / メモリ / GPU）に合うインスタンスへ**配置する**

つまり Batch = 「ECS on EC2 の前段に、ジョブキューとオートスケーラを付けたもの」。`ecs-tasks.amazonaws.com` や「ECS コンテナインスタンス」という単語が出てくるのは、この下敷きがあるから。

## 2. 登場する 3 つのリソースの役割分担

| リソース | 何を決めるか | 変更頻度 |
| --- | --- | --- |
| コンピューティング環境 (Compute Environment, 以下 CE) | **どんな計算資源を、どう調達するか**（インスタンスタイプ、SPOT/オンデマンド、最小/最大 vCPU、サブネット、SG、AMI、EBS） | 低い（インフラ都合） |
| ジョブキュー (Job Queue) | **どの CE にジョブを流すか**、キュー間の優先度 | ほぼ変えない |
| ジョブ定義 (Job Definition) | **何をどう実行するか**（イメージ、vCPU/メモリ/GPU 要求、環境変数、ログ設定、リトライ、タイムアウト、IAM ロール） | 高い（アプリ都合） |

「投入する」操作は `SubmitJob` API で、**ジョブ定義 + ジョブキュー**の 2 つを指定する。だから CE とジョブ定義は直接の依存関係を持たない。モジュールを 2 つに割る根拠がここにある（→ 02）。

## 3. ジョブ 1 本のライフサイクル

```
SubmitJob(jobDefinition=..., jobQueue=...)
  ↓
SUBMITTED → PENDING → RUNNABLE      ← ここで詰まったら「資源が足りない or 要求が満たせない」
  ↓ Batch が CE を見て EC2 を起動（min_vcpus=0 なら通常はここでコールドスタート）
  ↓ 起動テンプレートの GPU AMI で EC2 が上がり、ECS エージェントがクラスタに登録
STARTING                            ← ECR から image を pull（= 実行ロールの出番）
  ↓
RUNNING                             ← コンテナが動く（= ジョブロールの出番。S3 読み書き）
  ↓                                    stdout/stderr は awslogs ドライバで CloudWatch Logs へ
SUCCEEDED / FAILED
  ↓ ジョブが尽きると Batch が EC2 を落とし、vCPU が min_vcpus(=0) に戻る
```

**運用者として押さえる勘所**

- `RUNNABLE` で止まるのが Batch のトラブルの大半。原因は「max_vcpus が要求より小さい」「GPU を要求したのに GPU インスタンスが起動していない」「サブネットに IP がない」「SPOT のキャパシティ不足」「メモリ要求がインスタンスの利用可能量を超えている」など。**ジョブのログには何も出ない**ので、CE のイベントや EC2 の起動失敗を見にいく必要がある。
- `STARTING` で失敗 = ほぼ **実行ロール**の権限か ECR のイメージ不在。
- `RUNNING` で失敗 = アプリのバグか **ジョブロール**の権限不足。
- **コールドスタートは無料ではない**。`min_vcpus = 0` は「使わない間はタダ」の代わりに、EC2 起動 + GPU AMI ブート + 数 GB のイメージ pull で、実行開始まで数分かかる。バッチ用途なら妥当だが、起動待ちを何分と見込むかは設計時に確認する。

## 4. GPU が絡むことで増える制約

- GPU を使うには **NVIDIA ドライバ入りの AMI** が要る。SSM パブリックパラメータ `/aws/service/ecs/optimized-ami/amazon-linux-2023/gpu/recommended` から ECS GPU 最適化 AMI を引くのが定番（→ 04）。自前で AMI を焼く選択肢もあるが運用負荷が増える。
- ジョブ定義の `resourceRequirements` に `GPU` を入れると ECS が割り当てを行う。**GPU 数はインスタンス上限で頭打ち**なので、GPU 1 枚のインスタンスに GPU=1 のジョブを投げると 1 台 1 ジョブになる。
- **Fargate では GPU が使えない**。だから `platform_capabilities = ["EC2"]` で、Fargate 用のジョブモジュールとは分ける必要がある。
