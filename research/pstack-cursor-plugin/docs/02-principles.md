# pstack の21原則スキル調査

対象: `pstack/skills/principle-*`（全21ディレクトリ）の `SKILL.md`。
参考文脈: これらは `poteto-mode`（オーケストレーションの中核スキル）が「非負交渉事項」として全文参照する原則群で、AIが書く雑なコード（スロップ）を防ぐための規範集として機能している。

## 1. 原則スキルという設計

### なぜ原則を1つずつ独立スキルにしているのか

21個の原則は、すべて同じ形式に統一されている。

```yaml
---
name: principle-<kebab-case>
description: "Apply when ...(発動条件)... . (原則の要約)"
disable-model-invocation: true
---
```

この構造から読み取れる設計意図は次の3点。

**(1) 発動条件をdescriptionに埋め込み、本文をロード対象から切り離す。**
`description` は必ず "Apply when X" で始まり、どんな作業文脈でこの原則を思い出すべきかを一文で定義している。たとえば `principle-boundary-discipline` は "Apply when wiring validation, error handling, or framework adapters" であり、`principle-fix-root-causes` は "Apply when debugging" である。これは検索用のインデックスとして機能し、本文を読まなくても「今この原則が関係するか」を判定できるようにしている。

**(2) `disable-model-invocation: true` で自動発火を止め、`poteto-mode` からの明示参照に一本化する。**
全21原則がこのフラグを持つ。つまりこれらは独立して勝手にトリガーされるスキルではなく、`poteto-mode` の「Principles」セクションに一覧化され、そこから `**principle-xxx**` という名前で明示的に参照されて初めて読み込まれる設計になっている。`poteto-mode` の非負交渉事項には「マルチステップタスクの最初のtodoは必ずPrinciplesセクションを全文読むこと」「適用した原則ごとに、それが変えた具体的な決定を名指しすること」という強い縛りがあり、原則の引用を "決定に紐づく証拠" として要求している（「引用はあるが決定がない、は leaf skill を読んでいない証拠」）。

**(3) 1原則1ファイルによる独立更新性とクロスリファレンス。**
原則同士は本文中で `[Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)` のように相互リンクしている。1ファイル1原則にすることで、個々の原則を独立に改訂・追加・非推奨化でき、かつ「この原則とあの原則は別物だ」という境界線をSKILL.md自身が明示できる（例: `build-the-lever` は末尾で「`encode-lessons-in-structure` とは違う。あちらは再発する指示を恒久的なガードレールにするもの、こちらは目の前の作業のスループットと検証可能性の話」と自己申告している）。

つまりこれは「たくさんのベストプラクティスを1つの長いドキュメントに書く」のではなく、**発動条件付きの独立した意思決定ユニット**として原則を実装し、それを親スキル（poteto-mode）がカタログとして統括する、というアーキテクチャである。原則そのものがコードのモジュール設計の対象になっている点が特徴的。

## 2. 21原則の全カタログ

### principle-boundary-discipline（境界規律）
一言要約: 検証とエラーハンドリングはシステム境界に集約し、内部は無条件に型を信頼する。
核心の主張:
- 境界（CLI引数・設定ファイル・外部API・ネットワークプロトコル）でのみ検証・防御的処理を行い、内部コードは再検証しない。
- ビジネスロジックはフレームワーク非依存の純粋関数に置く。「殻は薄く機械的であるべき」。
適用例: 設定はパース時（＝境界）で検証し、ビジネスロジック内では検証しない。トランスポート/ストレージ/フレームワークの型を公開APIとして再エクスポートしない。判定質問として「このデータは今システム境界を通過しているか？」を提示。

### principle-build-the-lever（レバーを作れ）
一言要約: 自明でない作業は手作業でこなさず、それをやる/証明するツール自体を作る。
核心の主張:
- スループット（同じやり方を毎回再現し、無料で再実行できる）と信頼性（レビュアーが読んで再実行できる1つの成果物になる）の二重の見返りがある。
- 「原則を引用したのにdiffにcodemod・script・generator・delegate skillが無いなら、適用していない」という強い自己検証テストを持つ。
引用: "A deterministic script turns 'trust me' into 'run this'."

### principle-encode-lessons-in-structure（教訓を構造にエンコードせよ）
一言要約: 同じ指摘を2回書きそうになったら、それを文章ではなくメカニズム（lint・メタデータフラグ・ランタイムチェック・スクリプト）にする。
核心の主張:
- テキストの指示は「読み手が気づき、覚え、従う」ことに依存するため簡単に見落とされる。
- 「最も強い段（コンパイルできない表現不可能な状態 > CI で落ちる lint/禁止API > 正規のヘルパー > ランタイムチェック）」を選べという優先順位づけが明快。
- 「症状を紙で覆うな。修正が構造的なら、構造的な修正だけを使え。指示自体が症状である」という強いコロラリー。

### principle-exhaust-the-design-space（設計空間を使い尽くせ）
一言要約: 前例のないUI/アーキテクチャ判断では、実装前に2〜3案の競合プロトタイプを作って並べて比較する。
核心の主張: 間違ったものを作るコストは、3案を探索するコストより高い。「Design it twice」の言い換え。「最初の形の第2のバリエーションはカウントされない」と釘を刺している。
適用範囲外: コードベースに確立済みパターンがある機械的実装、明確な目標状態を持つバグ修正・リファクタ。

### principle-experience-first（体験を最優先せよ）
一言要約: 実装都合とユーザーの喜びが衝突したら、喜びを選ぶ。
核心の主張: 「製品とは体験そのものである」。1000個のことにNoと言う、多くの粗い機能より少ない磨かれた機能を出荷する、プロトタイプしてからコミットする、細部（遷移・整列・余白・フィードバック・エラー状態）にこだわる。
特徴的な拡張: 「ユーザー」を、UIのエンドユーザーだけでなく、ライブラリを import する同僚や、次にそのコードを保守するエンジニアにまで拡張している。

### principle-fix-root-causes（根本原因を直せ）
一言要約: デバッグ時、症状に絆創膏を貼らず、根本原因まで遡って直す。
核心の主張: 再現できないものは検証できない、「why」を根本原因に到達するまで問い続ける、クラッシュを黙らせるnilチェックガードの誘惑に抵抗する。「ワークアラウンドを正当化するのに段落サイズのコメントが要るなら、コードの方が間違っている」。
独自の追加ルール: 「再起動後に失敗する」バグは、コードではなく状態（設定ファイル・キャッシュ・ロックファイル・シリアライズされた状態）をまず疑え、という具体的なヒューリスティックを持つ。

### principle-foundational-thinking（基盤思考）
一言要約: ロジックを書く前にデータ構造を正しくする。構造的決定はオプション価値を守り、コードレベルの決定はシンプルさを守る。
核心の主張: 「データ構造の変更は、遅ければリライトになり、早ければ1行のdiffで済む」。並行性コロラリーとして「他のアクターが同時にこれを変更したらどうなるか？『何も起きない』でなければ隔離せよ」。スキャフォールドファースト（CI・lint・テストインフラ・共有型は後続フェーズ全てが恩恵を受けるので先にやる）。「Subtraction は scaffolding より先」と明記。

### principle-guard-the-context-window（コンテキストウィンドウを守れ）
一言要約: コンテキストウィンドウは有限かつセッション内で再生不可能な資源であり、入るトークン全てがその価値を証明すべき。
核心の主張: 大きなペイロード（詳細な出力・スクリーンショット・大きな文書）はサブエージェントに逃がし、メインコンテキストには要約だけを残す。使わないファイルは読まない。頻繁に使うテンプレートはスキルファイル内にインラインで持つ（別ファイル参照は毎回読み込みコストがかかる）。

### principle-laziness-protocol（怠惰プロトコル）
一言要約: コードを書くのはAIにとって安いからこそ過剰設計に陥りやすい。人間の保守担当者の疲労感を借りて対抗し、削除と最小変更に倒す。
核心の主張: リファクタや改善を頼まれたら追加の前にまず削除を探す。コールの階層をフラットに保つ（答えを得るのに3ファイル/レイヤー超えて追う必要があるならフラット化）。同じ判断を複数箇所で繰り返さず1つの真実の源に集約する。「新しいシグナルを型・スキーマ・パイプラインに通せと言われたら、立ち止まってより直接的な経路を探せ」。
引用: "If a human developer would find the code exhausting to maintain, it is a bad solution."

### principle-make-operations-idempotent（操作を冪等にせよ）
一言要約: クラッシュ・再起動・リトライが常態の環境で動く操作は、何度実行しても、どこから始めても正しい状態に収束するよう設計する。
核心の主張: 「これは2回連続で実行されたらどうなるか？前回の実行がどこかでクラッシュしていたらどうなるか？」を毎回問う。答えが「残された状態次第」なら、和解（reconciliation）ステップが必要。収束的起動・内容ベースのクリーンアップ・PIDベースの自己修復ロックといった具体パターンを挙げる。

### principle-migrate-callers-then-delete-legacy-apis（呼び出し元を移行してから旧APIを削除せよ）
一言要約: 新APIが正しい設計だと決めたら、互換レイヤーを残さず、呼び出し元の移行と旧APIの削除を同じリファクタの波で行う。
核心の主張: 内部の呼び出し元がまだ存在するというだけの理由で旧APIパスを生かし続けない。一時的なアダプタは例外的かつ期限付きとし、デフォルトのアーキテクチャにしない。旧実装の詳細だけを守るテストは削除する。
適用範囲: 外部ユーザーが後方互換性に依存していない、かつプロジェクトが協調的な破壊的変更を許容できる場合。

### principle-minimize-reader-load（読み手の負荷を最小化せよ）
一言要約: 保守性とは読み手が理解するために払う労力であり、「辿るべき層の数」と「保持すべき状態の量」という独立した2軸で計測する。
核心の主張: 呼び出し元1つだけのラッパーや、2つ目の実装がないアダプタなど、稼いでいない層は畳み込む。同じメソッド・同じ引数を繰り返すだけの隣接レイヤーは抽象度を稼いでいないので畳み込む。状態のスコープを縮める（純粋関数>ローカル>フィールド>モジュール状態>グローバルの順で好む）。判定テストは「新しい読み手が『Xはどこから来るか』『何がXを変更できるか』を30秒以内に答えられるか」。
`principle-guard-the-context-window` の「人間版」であると明言している点が興味深い（AIのコンテキストウィンドウと人間の作業記憶を同型の資源として扱う）。

### principle-model-the-domain（ドメインをモデリングせよ）
一言要約: 分岐しがちなロジックや、複数ファイルに散らばる形状の前提は、条件分岐の羅列ではなくデータ構造としてドメインを表現する。
核心の主張: 状態機械、型付きオブジェクト、マップ/レジストリ/判別共用体、リデューサ/コマンドイベントモデル、ドメイン知識でまとまったモジュール（load→validate→transform→saveのような実行順序でのまとめ方ではなく）などの構造カタログを提示。「実行順序は所有権ではない」という一文が鋭い。
サインの見分け方: 「既存のif/elseチェーンに1個分岐を足すだけの新機能」や「元のブール値と同期を保たねばならない2個目のブール値」がこの原則を見逃した兆候。

### principle-never-block-on-the-human（人間をブロックするな）
一言要約: 人間は非同期に監督する。可逆な作業では「Xしていいですか？」と聞かず、進めて結果を提示し、事後に人間が軌道修正する。
核心の主張: コードは安い、待機は高い。真に判断できない曖昧さのときだけ質問を取っておく。不可逆な操作（force-push・本番データ削除・外部へのメッセージ送信）だけは確認を要する。「プロダクトの方向性は人間から来るが、実行はブロックすべきではない」という線引き。

### principle-outcome-oriented-execution（成果指向の実行）
一言要約: 計画されたリライトやマイグレーションでは、滑らかな中間状態を保つことより、意図した検証可能な終着状態そのものを最適化する。
核心の主張: すべての中間ステップを完全に安定させようとすると、長期化する互換コードという負債を生む。中間的な破壊は、計画済み・スコープ済み・可逆であれば許容できる。完了前には必ず最終検証を走らせる。明示的なフェーズ境界を持つ計画的なリライト/マイグレーションにのみ適用。

### principle-prove-it-works（動くことを証明せよ）
一言要約: タスク完了後、宣言前に「本物」を直接チェックする。プロキシ・自己申告・「コンパイルは通った」では証明にならない。
核心の主張: プロセスの生存は間接的な派生状態ではなく直接確認する。委任した作業を検証するときは委任先の要約ではなくgit diffや実際の出力といった成果物そのものを検査する（「エージェントは意図したことを報告するのであって、実際に起きたことを報告するとは限らない」）。最も強い証明は決定論的なスクリプトによる再実行可能な比較であるとし、大規模・複雑な作業では成果物をコミットせよと具体的に指示する。

### principle-redesign-from-first-principles（第一原理から再設計せよ）
一言要約: 既存設計に新要件を継ぎ足すのではなく、その要件が最初から基盤的前提であったかのように再設計する。
核心の主張: 影響を受けるファイルを全て読んで現在の設計を全体として理解する。「もしこの新要件を知った上でゼロから書くなら何を作るか？」を問う。変更を型・ドキュメント・例・根拠セクションなど全ての参照箇所に伝播させる。「全体として設計し、段階的に届ける」。既存設計へのオプション価値を保つための方法論として位置づけられている。

### principle-separate-before-serializing-shared-state（シリアライズの前に分離せよ）
一言要約: 並行アクターが共有し得る可変状態を見つけたら、まず「本当に同じ可変オブジェクトを共有する必要があるか」を問う。不要なら共有を排除する。
核心の主張: 「取り合いで順番を守れ」という規約や指示は並行性制御にならない。デフォルトは共有書き込み先の排除（各アクターに専用のファイル/キー/ブランチ/状態ディレクトリを持たせ、読み取り/報告の境界でのみマージする）。「ロックが必要」は設計の匂いとして疑うべきものであり、デフォルトの答えにしてはいけない。

### principle-sequence-verifiable-units（検証可能な単位に並べよ）
一言要約: 作業を小さな単位に分割し、各単位を検証可能な状態で終わらせ、現在の単位が緑になるまで次に進まない。この規律を実行とデリバリの両方の高度で回す。
核心の主張: バッチ処理して最後に一度だけ検証するのではなく、各単位ごとに検証する。「バッチの後で見つかった壊れは埋もれ、既に壊れた基盤の上にさらに積み上げてしまっている」。デリバリでは、失敗するテストを先に、その上に修正を積む、という順序で「trust me」を「red になってから green になるのを見る」に変える。`prove-it-works`（各チェックを本物にする）と`build-the-lever`（単位ごとのチェックを安くする）の補完関係にあると自己申告。

### principle-subtract-before-you-add（追加の前に引き算せよ）
一言要約: システムを進化させるとき、まず複雑さを取り除き、それから構築する。削除がシンプルな土台を作り、次の追加を小さく脆くなくする。
核心の主張: 「複雑なシステムへの追加は複雑さを複利で増やす」。仕様が要求する以上の投機的なバリデータ・パーサ・ガードを作らない。「観測された使用パターンのために設計せよ、投機的なエッジケースのためではない」。新規性のない参照は、スタブとして残すのではなく削除せよ。「同じか、より小さい表面積の裏で、見つけた時よりわずかにシンプルで有能な設計にせよ」という継続的投資の姿勢。

### principle-type-system-discipline（型システム規律）
一言要約: 型チェッカーは証明支援器である。不可能な状態・プリミティブの取り違え・未処理のバリアントをコンパイル時に排除するために使う。
核心の主張:
- 「不正な状態を表現不可能にする」（`{completed: boolean; completedAt?: Date}` は `completed: true, completedAt: undefined` という無意味な組み合わせを許してしまう、という具体例が鋭い）。
- 「型は構築物であり、制約ではない」——非空リストは「長さチェック付きリスト」ではなく「head + rest」として構築する、という発想の転換。
- セマンティックなプリミティブへのブランド付け（`UserId` と `OrderId` を同じ文字列型にしない）。
- 外部データは境界でパースするまでは型が無い。
- 「型システムに嘘をつかない」——キャストや安全でない型強制は将来のランタイムクラッシュ。「今日埋めたキャストは来週書くポストモーテムだ」という引用が印象的。
- 網羅的パターンマッチはコンパイラの仕事にする。
- 権威あるスキーマ（protobuf・OpenAPI・GraphQL・DBマイグレーション・デザイントークン）から型を導出し、手書きの並行した型を作らない。
- 部分性が現れた場所だけ型を強化する——「他に何もパニックしないなら、素の型のままにせよ」という過剰精緻化への歯止め。

## 3. 原則間の関係

`poteto-mode` は21原則を5グループに分類しており（Core / Architecture / Verification / Delegation / Meta）、この調査でも同じ切り口が最も筋が良いことを確認した。ただし今回精読した本文の相互参照から、より細かい関係性が見える。

**コード品質・設計系（狭義のArchitecture）**
`model-the-domain`, `boundary-discipline`, `type-system-discipline`, `foundational-thinking`, `laziness-protocol`, `minimize-reader-load`, `subtract-before-you-add` は互いに強く連動する一群。`type-system-discipline` は本文中で `boundary-discipline` を名指しして「検証をどこに置くかはboundary-disciplineを見よ」と誘導し、`foundational-thinking` は「Subtraction は scaffolding より前」と `subtract-before-you-add` を前提に置く。`minimize-reader-load` は自ら「`guard-the-context-window` の人間版」と宣言しており、AI向け原則と人間向け原則が対になっている。

**変更管理・進化系**
`redesign-from-first-principles`, `outcome-oriented-execution`, `migrate-callers-then-delete-legacy-apis`, `subtract-before-you-add` は、既存システムをどう変化させるかという同じ問いに異なる角度から答える。前者2つは「新要件・新設計にどう向き合うか」、後者2つは「古いものをどう畳むか」という対応関係がある。

**並行性・実行時堅牢性系**
`make-operations-idempotent` と `separate-before-serializing-shared-state` は、明確にペアである。前者は「同じ操作が何度も走る」ケース、後者は「複数アクターが同時に走る」ケースで、どちらも「共有された可変状態」というテーマの表と裏。

**実行戦略・検証系**
`prove-it-works`, `fix-root-causes`, `sequence-verifiable-units`, `build-the-lever` は密結合している。`sequence-verifiable-units` は本文で自らを「`prove-it-works`（各チェックを本物にする）の並び替え補完」「`build-the-lever`（単位ごとの検証を安くする）の補完」と明記する。`build-the-lever` はさらに `encode-lessons-in-structure` と `prove-it-works` の両方から自分を差別化する記述を持ち、3すくみの関係を自己申告している。

**コンテキスト・委任系**
`guard-the-context-window` と `never-block-on-the-human` はどちらも「エージェントが人間やコンテキストという有限資源をどう扱うか」という同じ問題意識の異なる面。`minimize-reader-load` が前者の人間版であることは前述の通り。

**メタ系**
`encode-lessons-in-structure` は他の全原則がどう強制されるべきかを扱う、いわば「原則についての原則」であり、pstack自体の自己参照的な設計思想（テキストの指示を書くのではなく構造化する）を体現している。実際、原則スキル群自体（発動条件をfrontmatterに構造化し `disable-model-invocation` で制御する設計）はこの原則の実践例そのものになっている。

**やや独立している原則**
`experience-first` と `exhaust-the-design-space` は、他の18個がほぼ「コード生成・実行の作法」であるのに対し、この2つだけがプロダクト/UX判断という異なるレイヤーを扱っている。ただし`experience-first`は「ファウンデーションは体験に奉仕するのであって逆ではない。ファウンデーション思考は作業の順序を統治し、この原則はターゲットを統治する」と`foundational-thinking`との役割分担を自ら明記しており、孤立してはいない。

## 4. 所感

### 特に鋭い・独自性のある原則トップ5

**1. principle-encode-lessons-in-structure**
「同じ指示を2回書きそうになったら、テキストではなくメカニズムにする」という発想自体は目新しくないが、「最も強い段（コンパイル不可能な表現 > CIで落ちるlint/禁止API > 正規ヘルパー > ランタイムチェック）を選べ、なぜならエージェントは周囲のコードが既にやっていることを模倣するので、弱いガードは次のテンプレートになる」という理由づけが独自。これはAIコーディングエージェント特有の「模倣によるパターン伝播」という性質を的確に突いており、人間の開発チームへのアドバイスの単なる焼き直しではない。

**2. principle-never-block-on-the-human**
一般的な自律エージェント設計論の焼き直しに見えるが、「人間は非同期に監督する」「コードは安い、待機は高い」という経済モデルを明快に立て、可逆/不可逆の境界線（force-push・本番データ削除・外部メッセージ送信のみ確認要）を具体的に引いている点が実用的。AIエージェント運用というこの文脈固有の課題（過剰な確認要求によるスループット低下）にピンポイントで刺さっている。

**3. principle-guard-the-context-window（と対をなすminimize-reader-load）**
コンテキストウィンドウという、AIエージェント特有の有限資源をまず定義し、それを人間の作業記憶と同型のものとして`minimize-reader-load`に接続する発想が秀逸。「働かない層を畳み込め」という古典的な設計原則を、AIとその読み手（人間）両方に共通する「有限な処理容量」というフレームで統一しており、単なるDRY原則の言い換えを超えている。

**4. principle-type-system-discipline**
型システムに関する個別のテクニック（判別共用体・ブランド型・網羅的マッチ）自体は業界のベストプラクティスだが、「型は構築物であり制約ではない」（非空リストはhead+restとして構築するのであって、長さチェック付きリストとして絞り込むのではない）という切り口と、「部分性が現れた場所だけ型を強化せよ、他に何もパニックしないなら精緻化するな」という過剰型付けへの歯止めが独自性を持つ。多くの型駆動設計の議論は「もっと厳密に」に振れがちだが、この原則は逆方向のブレーキも明示している。

**5. principle-build-the-lever**
「原則を引用したのにdiffにcodemod/script/generator/delegate skillが無いなら適用していない」という自己検証可能なテストを組み込んでいる点が、単なる心構えの提示に留まる他の多くの原則と一線を画す。原則の適用有無を成果物の有無で機械的に判定できるようにしている稀有な例。

### 一般的なベストプラクティスの焼き直しに近いもの

- **principle-fix-root-causes** は「再現してから直せ、根本原因を追え」という、デバッグの教科書的な内容そのもの。「再起動後のバグはコードでなく状態を疑え」という付け足しは実用的だが、原則全体としての新規性は薄い。
- **principle-laziness-protocol** は本質的にYAGNI/KISSの言い換えであり、「人間の保守担当者の疲労感を借りる」という比喩は説得力があるものの、内容自体は既存の議論の範囲内。
- **principle-boundary-discipline** はHexagonal Architecture / Parse-don't-validate の議論をほぼそのまま踏襲しており、独自の主張は薄い（ただし`type-system-discipline`との組み合わせ方は良い）。
- **principle-exhaust-the-design-space** は "Design it twice" という既存のフレーズをそのまま引用しており、原則としての独自貢献は「いつ適用しないか」の線引き程度。

総じて、21原則のうち「コード生成AI特有の失敗モード（模倣による弱いガードの伝播、委任先の自己申告への過信、コンテキスト消費、確認待ちによるスループット低下）」を明示的に狙い撃ちしたものは独自性が高く、一般的なソフトウェア工学の教訓を移植しただけのものは相対的に凡庸という傾向が見られた。
