# assistant position

## 主張の核

GitHub を捨てるかどうかより, GitHub をコードとレビューの基盤として残したまま, AI エージェントが必要とする context 基盤を別レイヤーで補強すべきかを議論する方が現実的である.

## 問題提起への評価

問題提起は妥当である.

AI 開発の生産性は, コードそのものより, 必要なコンテキストをどれだけ継続的に参照できるかに強く依存する. その認識に立つと, GitHub は `system of record` としては強いが, `system of context` としては十分でない可能性がある.

## GitHub の強い領域

- Git 管理
- PR / review
- 権限管理
- CI 連携
- 監査性
- エコシステム

このため, すぐ全面移行を考えるのは現実的ではない.

## 重要な整理

論点は次のように置くのがよい.

- GitHub をやめるか
- ではなく, GitHub をどこまで中核に残し, どこから外部基盤に任せるか

## 外部 SaaS ではなく自作する判断

この判断には合理性がある.

- まだ市場が十分こなれていない
- 小さく自作することで, 自分たちの開発フローに合った shape に寄せやすい
- 組織内に, AI 開発基盤をどう作るかの知見が残る

ただし, 自作するなら, 何に依存して作るかが次の論点になる.

## 設計上の立場

二者択一にしない方がよい.

- interface は GitHub に近づける
- state は AWS 側に寄せる

つまり:

- ユーザー体験やトリガーは GitHub 起点でもよい
- ただし, 蓄積するコンテキスト, artifact, index, memory, metadata は AWS 側に逃がす

## 設計原則

### GitHub に寄せてよいもの

- イベント起点
- レビュー導線
- 開発者操作の入口

### GitHub に寄せすぎない方がよいもの

- artifact 本体
- 長期保存データ
- 検索インデックス
- エージェント memory
- コンテキストの正規メタデータ

## 暫定結論

- GitHub は今後もしばらく主軸に残る可能性が高い
- しかし, AI エージェント時代の開発基盤として単体では不十分になっていく可能性も高い
- したがって, 議論すべきは GitHub 継続可否ではなく, GitHub を中心に何を追加し, どこから別基盤に任せるかである
- 自作するなら, GitHub 直結で完結させるより, GitHub を入口にしつつデータ蓄積は AWS 側へ逃がす設計が最もバランスがよい
