# nakatani position

## 主張の核

GitHub はコードホスティング基盤としては依然強いが, AI エージェントを前提にした開発基盤として最適とは限らない.

AI の開発パフォーマンスは, コードそのものより, 周辺コンテキストをどれだけ蓄積し, 利用できるかに強く依存する. その観点では, GitHub 単体の受け皿は狭い可能性がある.

## 前提

- AI を使った開発は今後も主流であり, 逆行しない
- AI の性能はコンテキスト量と質に大きく依存する
- 必要なコンテキストは, GitHub が従来中心的に扱ってきたコードや PR を超える

対象には以下が含まれる.

- 手順書
- 設計メモ
- 画像
- 調査結果
- 大量データ
- 実験履歴
- その他の非コード資産

## 同意している点

- GitHub 固有機能への依存は既に強く, 簡単には移行できない
- 価格を理由に他へ乗り換える可能性は低い

## それでも論点が残る理由

問題は価格ではなく, パフォーマンスである.

より正確には:

- AI / agent 開発の生産性を高めるうえで, GitHub のままで十分か
- 十分でないなら, 別基盤への移行か, GitHub への追加レイヤーが必要ではないか

## 追加の前提

- GitHub に不足している機能を外部 SaaS で補う方向は, まだ十分整っていない
- 組織内で知見を貯める価値もあり, ある程度は小さく鋭く自作したい
- したがって, 問いは「買うか作るか」より「何をどう自作するか」に近い

## 迷っている設計判断

### 1. GitHub 前提で作る

- GitHub を使い続ける限り, 相性の良いツール群を組みやすい
- PR, repository, issue, Actions, App, Webhook などと自然に接続できる
- その分, GitHub 固有モデルへの依存が強くなり, 将来の移行コストは高くなる

### 2. AWS を基軸に作る

- GitHub より息の長い基盤を中心に据えられる可能性がある
- ストレージ, 検索, 権限, データ処理などを比較的中立に設計しやすい
- 一方で, 目先の開発体験や GitHub との親和性は弱くなりうる

## 迷いの本質

短中期の開発速度と, 長期の可搬性・自由度のどちらを優先するか, というトレードオフである.

## 問題設定

- GitHub 依存が強いので簡単には移行しない
- 価格起点では乗り換えない
- しかし, AI エージェント開発に必要なコンテキスト基盤として GitHub が最適かは別問題
- そのため, 追加基盤は必要になりうる
- その追加基盤を GitHub 前提で作るか, AWS 基軸で作るかが現在の主要論点である
