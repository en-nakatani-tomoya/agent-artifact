# Agent Context Platform Strategy

## 問い

AI エージェントを前提にした開発が主流化する中で, 開発基盤の中心を何に置くべきかを整理する.

出発点は GitHub のライフスパンに関する疑問だったが, 議論を進めると本質は別にあった.

- GitHub を今後 10 年使い続ける前提を置いてよいのか
- GitHub は AI エージェント時代の開発基盤として十分か
- 不足があるなら, GitHub に寄せて補うのか, より中立な基盤を別に持つのか

## 背景

従来の開発基盤では, コード, PR, CI, 権限管理が中心だった. GitHub はこの領域で非常に強い.

一方で, AI エージェントの開発パフォーマンスは, コードだけでなく, 周辺コンテキストをどれだけ継続的に蓄積し, 取得し, 再利用できるかに大きく依存する.

必要なコンテキストの例:

- 手順書
- 設計判断
- 調査メモ
- 画像
- artifact
- 実験履歴
- 大量データ
- 運用ログや検証結果

この変化により, GitHub は依然として強い `system of record` ではあるが, `system of context` としては十分でない可能性がある.

## この調査で見ている論点

1. GitHub を中心に据え続ける前提はどこまで妥当か
2. GitHub の不足は価格ではなく, AI 開発の性能上限として現れるのではないか
3. 不足領域を外部 SaaS で埋めるのではなく, 小さく自作する価値はあるか
4. 自作するなら, GitHub 前提で作るべきか, AWS 基軸で作るべきか

## 前提認識

- GitHub 固有機能への依存は既に強く, よほどの理由がない限り簡単には移行できない
- 価格を理由に GitHub から乗り換える可能性は低い
- しかし, AI エージェント開発に必要な基盤として GitHub が最適かは別問題
- 外部サービスを積み増す方向はまだ整っておらず, 組織内知見の蓄積も考えると, ある程度小さく自作したい

## 議論の整理

この問題は「GitHub を捨てるか」という単純な二択ではない.

現実的には, 次の 3 つを比較する必要がある.

1. GitHub 前提で不足機能を補う
2. AWS 基軸で context 基盤を作り, GitHub は一つの入力ソースとして扱う
3. GitHub を入口に使いながら, 蓄積データは AWS 側へ逃がす

現時点では 3 が最もバランスがよい.

## 暫定結論

短中期では GitHub をコードとレビューの中核として残すのが自然である.

ただし, 以下を GitHub に閉じ込めすぎない方がよい.

- artifact 本体
- 長期保存データ
- 検索インデックス
- エージェント memory
- コンテキストの正規メタデータ

つまり, 開発者の操作導線やイベント起点は GitHub に寄せてもよいが, context の実体は GitHub から分離した方がよい.
