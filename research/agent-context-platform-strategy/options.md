# Options

## Option 1. GitHub 前提で作る

### 概要

GitHub を中心基盤とみなし, 不足機能を GitHub 周辺の拡張として積み上げる.

### 強み

- 既存フローに自然に乗る
- PR, repo, issue, Actions, Webhook, App と接続しやすい
- 目先の開発速度を出しやすい

### 弱み

- GitHub 固有モデルへの依存が強くなる
- 後から別基盤へ移るコストが高い
- artifact や context の実体まで GitHub 側へ寄せやすい

### 向いている状況

- まず短期間で体験を作りたい
- 将来の可搬性より, 現在の開発生産性を強く優先する

## Option 2. AWS 基軸で作る

### 概要

GitHub は入力ソースの一つとして扱い, context の蓄積と検索の中心を AWS 側に置く.

### 強み

- ストレージ, メタデータ, artifact, indexing, retrieval を比較的中立に設計できる
- 将来別の SCM や実行基盤に広げやすい
- GitHub の寿命と切り離して考えやすい

### 弱み

- 最初の統合作業が重い
- GitHub との親和性は直結案より弱い
- 目先の体験構築はやや遅くなる

### 向いている状況

- 長期の可搬性や基盤寿命を重視する
- 既に AWS 側にデータ基盤を寄せる思想がある

## Option 3. GitHub を入口にして, データは AWS に逃がす

### 概要

操作導線とイベント起点は GitHub に寄せつつ, context の実体は AWS 側で管理する.

### 強み

- 既存の GitHub 体験を活かせる
- 将来の可搬性も確保しやすい
- control plane と data plane を分離できる

### 弱み

- 境界設計が曖昧だと複雑になる
- GitHub と AWS の責務分離を明確に保つ必要がある

### 向いている状況

- 今の開発体験をあまり壊したくない
- ただし GitHub へのロックインも深めたくない

## 現時点の推奨

現時点では Option 3 が最も現実的である.

理由:

- GitHub 依存の強さを前提に, 目先の体験を壊しにくい
- 一方で artifact, memory, metadata を GitHub に閉じ込めずに済む
- 将来 GitHub 以外の基盤を使う場合にも差し替えやすい
