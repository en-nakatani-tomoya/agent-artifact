# ddd entity fit for consumed data and batch pipelines

## 概要
推薦結果のように「届けられて消費される」データや読んで変換して書くバッチパイプラインに、DDD のエンティティ / アグリゲートは噛み合わない。値オブジェクト・ドメインイベント・ユビキタス言語・コンテキスト境界だけを使い、DDD の分類語をディレクトリ名に含めないのが整合する。

## 詳細
### 前提: DDD のエンティティと値オブジェクトの定義

- **エンティティ**: 属性ではなく同一性（identity）で区別され、時間を通じて連続性を持ち、状態が変化しうるオブジェクト
- **値オブジェクト**: 同一性を持たず、属性の値だけで等価性が決まる不変のオブジェクト
- エンティティ・アグリゲート・リポジトリの三点セットは「同じものが何度も読み書きされ、整合性を保ちながら変更され続ける」問題のための道具

### 推薦結果のような「消費されるデータ」はエンティティではない

- 生成されて、届けられて、消費されたら終わり。次の run で同じ user_id に出るものは「更新された同じ推薦」ではなく別の推薦
- 誰も部分更新しないので、不変条件を守るトランザクション境界（アグリゲート）が要らない
- 「先週のあの推薦」を指すには run と user_id の組で足り、それは参照であって同一性ではない
- 本質は値であり、イベント的な「事実の記録」。DDD の語彙では値オブジェクトかドメインイベントに近い

### 同じことはバッチ / 変換パイプライン全体に言える

- 入力側の「ユーザ」「商品」も、業務システム上ではエンティティだが、パイプラインに届いた時点では「ある時刻のスナップショットを列指向に並べたもの」で、読むだけで変更しない
- 抽出→変換→出力の中に状態遷移するものが無い。これは推薦固有ではなく分析・変換パイプラインに共通する性質
- データエンジニアリングが「テーブル」「カラム」「スキーマ」「不変スナップショット」で語るのは、この性質に合った語彙だから

### それでも DDD から残るもの

戦術パターン（entity / aggregate / repository）を外しても、次はパイプラインでも効く。

- **ユビキタス言語**: 業務側と同じ語で概念を呼び、コードにもそう書く
- **境界づけられたコンテキスト**: ステージごとに別モデルを持ち、契約（スキーマ）で繋ぐ構造はコンテキスト境界そのもの
- **値オブジェクト**: コンストラクタで検証し、以降は「検証済み」を型で渡す
- **ドメイン層の隔離**: 後段の層が前段で足した属性の存在を知らない、という関心事分離

### 命名・配置への帰結

- 不変の列指向コレクションや出力レコードを `domain/entity/` に置くのは定義上の誤用
- DDD の分類語（entity / value_object / aggregate）をディレクトリ名に含めず、概念名（`user/` `job/` `recommendation/`）で置くと、定義との整合を問われる余地が消える
- 複数形のクラス名（`Users` / `Jobs`）は、単数の `User` クラスが存在しない限り曖昧にならない。`UserPopulation` / `UserSet` / `UserCollection` は容れ物の形を説明する語で、概念ではなく表現を名前にしてしまう

### エンティティが再登場する場所

消費されるデータの側でも、「配信履歴」「ユーザが推薦をどう扱ったか（クリック・応募・非表示）」を蓄積して次の推薦に使い始めた時点で、ユーザ単位の状態・同一性・ライフサイクルが生まれ、エンティティが意味を持つ。

### 整理

- 状態を持ち変更され続けるデータ → entity / aggregate / repository が効く
- 届けられて消費されるデータ、読んで変換して書くパイプライン → value object / domain event / ubiquitous language / bounded context だけを使う
- DDD を「戦術パターン一式を揃える方法論」と受け取ると相性の問題が出るが、「業務の概念をそのままモデルの語彙にする」という中核だけ取れば推薦バッチともよく合う
