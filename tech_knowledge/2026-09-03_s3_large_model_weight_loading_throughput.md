# s3 large model weight loading throughput

## 概要
S3 上の巨大な単一ファイル（26.7 GiB の model.safetensors）を GPU へロードする際の高速化手法を実測比較した記録。ダウンロード並列化とマウント方式の違い、および逐次ベンチでストレージを選ぶと実ワークロードで逆の結論になる罠。

## 詳細
## 前提となった構成

GPU インスタンス（L40S 1 枚）上の vLLM で、26.7 GiB の単一 `model.safetensors`（FP8 量子化済み MoE モデル）を S3 から読み込むバッチ。ロード時間がジョブ全体の 72%（1,551 秒中 1,119 秒）を占めていた。

## 1. 遅さの正体は「S3 が遅い」ではなく「ストリームが 1 本」

S3 は 1 本の TCP コネクションあたりのスループットに実質的な上限があり、アグリゲート帯域はコネクション数で稼ぐ設計になっている。

`pyarrow.fs.copy_files` の並列度は **ファイル単位**。したがって巨大な単一ファイルは何をしても 1 ストリームに落ちる。実測 25.6 MB/s は S3 の速度ではなく 1 コネクションの速度だった。

boto3 の `TransferConfig`（マルチパート並列ダウンロード）に差し替えると 208 秒 = 138 MB/s で 5.4 倍になる。同じ 1 ファイルをレンジ GET で分割して複数コネクションに散らすため。`aws s3 cp` が速いと言われるのも中身はこの s3transfer エンジンそのもので、速さの出所はコマンドではなく並列レンジ GET にある。

## 2. マウントが効くのは「往復が消える」から

ダウンロード方式とマウント方式の本質的な差は並列度ではなく、バイトが何回運ばれるか。

| 方式 | バイトの経路 | 26.7 GiB を運ぶ回数 |
| --- | --- | --- |
| ダウンロード（copy_files / boto3 / aws s3 cp） | S3 → EBS へ書く → EBS から読む → GPU | 2 回・直列 |
| マウント（S3 Files / Mountpoint） | S3 → ページキャッシュ → GPU | 1 回 |

- ダウンロード完了を待ってからロードを開始する、という直列の待ちが構造的に消える
- EBS を経由しないので gp3 のスループット上限を踏まない（既定 125 MiB/s では 26.7 GiB の書き込みだけで 219 秒の床ができる。ここを明示的に 250 MiB/s にしてあるかどうかで過去の計測結果が大きくブレていた）
- アプリからはローカルパスを開いているだけに見え、並列レンジ GET はマウント層が引き受ける。アプリ側のダウンロード処理コードを丸ごと削除できる

## 3. 最大の学び: 逐次ベンチで選ぶと逆の結論になる

同一インスタンス・同一ファイルで Amazon S3 Files（NFS v4.2 / EFS ベース）と Mountpoint for Amazon S3（FUSE）を比較したところ、マイクロベンチと実ワークロードで**順位が逆転した**。

| | 単一スレッド逐次読み（dd / mmap） | vLLM の実ロード |
| --- | --- | --- |
| Mountpoint | **971 MB/s** | 185 MB/s（7 割減） |
| S3 Files | 277 MB/s | **424 MB/s**（1.5 倍増） |

理由はアクセスパターン。vLLM の safetensors ロードはヘッダを読んだあと**テンサ単位でシークして拾う**ので、ファイルを頭から舐める動きにはならない。実質ランダムアクセス＋並行アクセスになる。

- **Mountpoint** はオブジェクト単位の逐次プリフェッチに最適化されている。先読みした範囲と違うオフセットに飛ばれるたびに先読みが無駄になりやり直しになるため、逐次では最速なのに実ロードでは崩れる。この兆候はマイクロベンチ段階でも並列読み 83.1 秒 対 逐次 29.5 秒という形で見えていた
- **S3 Files** は NFS なのでクライアントが独立した RPC を並行に飛ばせる。順序が飛んでも各リクエストが独立しているため崩れず、並行度が上がった分だけ**逐次より速くなった**

Mountpoint 側の劣化理由はプリフェッチ設計と上記の並列読み劣化からの推論で、内部計装は取っていない。順位そのものは実測。

**教訓: ストレージ層の選定を `dd` や `mmap` の逐次ベンチだけで判断してはいけない。実際のアクセスパターンで測らないと逆の結論が出る。** 今回、逐次ベンチだけを見ていれば Mountpoint を選び、本番で 2.3 倍遅い構成を採用していた。

## 4. 結果と次のボトルネック

| 方式 | 重み取得 | 現状比 |
| --- | --- | --- |
| pyarrow.fs.copy_files | 1,119 秒 | — |
| boto3 マルチパート → EBS → 読む | 208 秒 | 5.4 倍 |
| Mountpoint + vLLM | 154 秒 | 7.3 倍 |
| **S3 Files + vLLM** | **67.5 秒** | **16.6 倍** |

I/O を潰すとボトルネックが移る。67.5 秒になった時点での内訳は 重み取得 70.5 秒 / エンジン初期化 121.3 秒（うち **torch.compile 65.2 秒**）。`docker run --rm` が `/root/.cache/vllm/torch_compile_cache` を毎回破棄しているため、コンパイル 65 秒を毎 run 支払っていた。ここから先は I/O をさらに倍速にしても取り分 34 秒に対し、コンパイルキャッシュの永続化が 65 秒。**投資対効果が逆転する**。

## 5. 採用時の前提条件の差

| | S3 Files | Mountpoint |
| --- | --- | --- |
| 実体 | NFS v4.2/4.1（EFS ベース） | FUSE（静的バイナリ） |
| バケット側の要件 | **バージョニング有効 + SSE-S3/SSE-KMS が必須** | なし |
| ネットワーク | VPC 内にマウントターゲット + TCP 2049 | 不要 |
| IAM | ファイルシステム用サービスロールが別途必要 | インスタンスロールのみ |
| クライアント要件 | amazon-efs-utils >= 3.0.0 / AWS CLI >= 2.34 | rpm を入れるだけ |
| nconnect | **非対応** | — |
| 読み取り上限 | クライアントあたり 3 GiB/s。1 MiB 以上の読みは S3 から直接ストリームされ、ファイルシステムのデータ転送料金がかからない | — |

S3 Files の方が速いが、バケットのバージョニング必須・マウントターゲット・追加 IAM ロールと前提条件は重い。Terraform 化のコストを含めて判断する。

なお「Mountpoint は mmap 非対応」というコミュニティ報告があるが、1.24.0 では mmap は動作した（かつ逐次ベンチでは最速だった）。Docker に FUSE マウントを見せるには `--allow-other` が必要。
